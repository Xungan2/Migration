# P1 功能裁剪处置

你处理功能子集迁移后，保留代码仍引用的驱动自有符号。输入由词法扫描
产生，只是候选；是否可达、是否为同名噪声、如何维持用户要求的行为，
需要你读源码判断。在一次任务中完成全部候选及所选补回引入的依赖。
机器随后只校验方案；遗漏或依赖环会使任务停止，不再开启分析轮次。

1. 读 goals.md、scope.json 的功能保留/排除/约束和 strategy.md。目标是
   用户要求的功能，不以编译通过代替语义正确。
2. 对每项读原始定义及保留调用点。沿成功路径、失败回收、注销销毁、
   回调表、初始化数组核实。扫描也会找到文件白名单之外的定义。
3. 选择处置并说明实现步骤与可观察验收：
   - restore：必要实现被误裁，补回已审文件范围内的源码，指定 source
     和现有 module。读 pruning_context.json 中该符号的 restore_spans
     和 references，沿所选补回的依赖继续分析，在同一份 decisions 中
     给出需要补回或处置的依赖。对照 deps.json 选择不会产生环的归属。
     多个消费者共用同一定义时选择一致的 module，只补回一份源码。
   - rewrite：在目标语言实现明确的等价逻辑。写出分支、返回值、
     状态变化和资源生命周期；P4 将消费这些说明。
     Linux 的 kobject、sysfs 等名称是源端机制说明，不能据此假定
     目标 OS 有同名 API，或要求重建已排除的控制接口。描述原生设备
     登记、引用计数和释放等待等可观察语义，具体 API 由后续映射核实。
   - remove_path：引用仅服务于已排除功能。明确要移除的调用、初始化
     项、分支或回调及其清理对称项，解释保留路径为何仍然成立。
   - not_applicable：字段、局部名称、宏拼接或其他词法误判。给出源码
     证据，说明为什么这里没有对被裁实现的真实依赖。
4. evidence 使用相对路径:行号，原始定义相对 Linux 驱动目录，模块
   引用相对迁移工作区（P1/modules/...）。每项至少一条可读取证据。
5. implementation 与 verification 针对 P3/P4 生成的目标 OS 代码和
   运行行为。P1/modules 是只读的迁移参考，路径与行号只定位修改的
   语义来源；静态残留检查应检查目标 OS 产物，不要求改写 P1 源片段。
6. 提交前检查闭包：每个输入 id 恰好一项决定；每个 restore 引入的
   驱动依赖均已保留、在本方案中补回，或有明确处置。潜在依赖表是
   保守扫描，按实际所选路径查阅；无需对未激活的假设路径逐项输出。
   扫描不能代替源码核查。方案无法完整闭合时输出 blocked 和具体原因。

guardrail：必要行为不能用空函数、无条件成功或未经证明的“不可达”
替代。范围外源码可作等价改写的参考；restore 只在已审文件范围内。
本任务只读输入并输出决定；方案改动和编译由流水线执行。

输出协议由调用方注入。decisions 列表中每项：

    {"id":"输入的原始id","action":"rewrite",
     "reason":"为何符合已审功能范围",
     "evidence":["core.c:123","P1/modules/core/core.c:56"],
     "implementation":"P4 须实施的具体逻辑或路径修改",
     "verification":"能发现语义错误的测试及预期结果"}

restore 额外给 "source":"core.c","module":"已有模块名"。
补回引入的新依赖使用 "id":"补回后引用所在模块:符号名"，符号须来自
pruning_context.json 的 dependencies。其 evidence 引用原始 Linux 源码，
模块必须是已有模块；格式与输入候选的决定一致。

例如保留代码调用已裁 A，而 A 调用已裁 B：同一份方案给出 A 的 restore，
以及 B 的 restore/rewrite/remove_path/not_applicable，机器一次应用并校验。
保持 JSON 紧凑；理由与实施方案具体到本项。
