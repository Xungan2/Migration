# P0 最小前置依赖识别

在主驱动骨架施工前，识别让它能够被构建、匹配并认领设备所需的最小前置
能力。读取项目资料与迁移意图，从 Linux 注册入口、调用接口和构建依赖
追到提供者；允许读取 Linux 参考根内、主驱动目录外的源码。

1. 确认源驱动身份、匹配条件及本次目标平台。平台未定而依赖选择受其影响时，
   生成 status=unknown 的平台选择任务，避免猜定控制器或扩大到整套子系统。
2. 列出最小能力依赖图。包含外部总线/框架、所选控制器、基础服务，以及
   输入目录内但必须先就绪的依赖。递归到目标已提供的能力或可单独完成的
   前置迁移任务；只纳入当前构建、认领和测试所必需的部分。
3. 对每项查目标源码：available=已有对应接口及接线，并给出实际原文证据；
   missing=确认缺失；unknown=证据不足。target_status 写清调查范围和结论。
   已有功能可复用，无须照搬 Linux 实现。源码存在不等于构建接线或语义对应。
4. 为每项给出限定范围的 action、Linux source_files 和可核对的 acceptance。
   missing/unknown 会转成前置任务并阻塞主驱动；任务依赖写 depends_on。
   即使依赖位于主输入目录内，也要明确先后关系，不把主驱动本体列为自己的
   前置任务。能力无前置依赖时显式写空数组并在 binding 解释认领入口。

认领对象以源驱动及迁移意图为准，不能用其他设备替代；组件驻留、MISS 日志、
命令行字符串变化均不是设备匹配证据。缺失能力须保留为任务，不通过降低
验收标准标成 available。用户填写任务完成或旧报告声称可用，均须查当前源码。

本任务只读源码，写指定报告；不迁移代码、不修改主驱动范围、不运行构建或
启动。主驱动的三个 loop 仍负责最终运行验收。报告可以成功描述一个被阻塞
的项目，不必为了让项目通过而把缺失依赖说成可用。

输出裸 JSON 到指定文件：

```json
{
  "subject": "源驱动身份与注册入口",
  "platform": "目标硬件或仿真平台；未确定时如实说明",
  "binding": "匹配条件、认领路径及依赖范围说明",
  "source_evidence": [{"path": "Linux参考根内相对文件路径", "line": 1, "quote": "该行原文子串"}],
  "dependencies": [{
    "id": "capability-id",
    "capability": "能力名称",
    "reason": "为什么是当前主驱动的必要前置",
    "depends_on": [],
    "status": "missing",
    "source_files": ["Linux参考根内实际文件路径"],
    "source_evidence": [{"path": "Linux参考根内相对文件路径", "line": 1, "quote": "该行原文子串"}],
    "target_status": "目标侧已有实现或缺失/待确认的具体事实与调查范围",
    "target_evidence": [],
    "action": "需迁移、原生补齐、选择或验证的最小范围；已有能力写复用方式",
    "acceptance": ["对应接口、构建接线及能力验证的完成条件"]
  }],
  "handoff_summary": "依赖结论及主驱动是否被阻塞"
}
```

target_evidence 的 path 相对目标树；available 项必须有非空证据，其他项
允许为空。所有引文必须命中指定文件行。depends_on 只引用本报告 id，禁止环。
报告保留能力与证据，不填写日期或人工完成状态；编排器生成任务清单。
