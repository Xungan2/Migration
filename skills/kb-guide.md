# SKILL: 知识库使用总纲（kb-guide）

> 本总纲随所有带知识面的 agent 调用注入。你本次任务 prompt 中的
> "知识库条目目录"块由编排器按任务类型选定了相关子目录。

## 规则 0（强制——先检索后动手）

**在开始处理任务本身之前，你必须先检索本次 prompt 中提供的知识库
条目目录（INDEX）。** 若存在与当前任务相关的条目：

1. **必须读取该条目全文**后再动手；
2. 不得在未检索的情况下断言"无先例"，也不得绕过已有结论自行
   发明绕过方案——若你认为历史结论已过时，须给出当前源码/环境
   中重新核实过的证据；
3. 完成后在结构化输出 JSON 中附 `kb_consulted` 字段（数组：
   本次实际读过的条目文件名，原样照抄 INDEX 的 file 值；未读任何
   条目则省略该字段）。

知识库是历次迁移实证经验的沉淀——同类问题大概率已被解决过，
忽略它是最高成本的错误。

## 知识库结构（三区）

```
knowledge/
├── base/      # 工具随附的一般知识（任意目标 OS 可用；已审）
├── temp/      # 本次运行中的草稿（未经人审——可用，但与已审内容
│              # 冲突时以已审为准，且不得未核实就照抄）
└── <本次目录>/ # 本次迁移的知识库目录（p0 时由用户指定；已审）
```

## 子目录（= 知识分类）

| 子目录 | 内容 | 一条目粒度 |
|---|---|---|
| maps/ | Linux API → 目标 OS 对应物映射表（`驱动@目标.md/.json` 双文件，机器表为 .json） | 一驱动@目标一张整表 |
| gaps/ | API 缺口处置：某 Linux API 无对应物时怎么绕、fill 补齐成败与原因 | 一个 API 一个文件（文件名即 API 名） |
| runbook/ | 目标 OS 操作手册：怎么构建/启动/跑内核态测试（含坑史 notes） | 一主题/一坑一文件 |
| splits/ | 拆分策略样例（strategy.md 原样） | 一驱动一文件 |
| pitfalls/ | 踩坑记录：平台/模拟器坑与方法教训（复合缺陷分解、判别方法等） | 一坑一文件 |

## 使用铁律

1. **核实后采用**：条目是历史主张，不是真理——evidence 的 file:line
   在源码树演进后可能失效，必须在**当前**目标树/环境中重新核实；
2. **不跨目标复用未验证结论**：`e1000@asterinas` 的结论对其他驱动
   只是线索；runbook 命令在环境漂移（换机器/镜像/缓存清空）后可能
   失效，本轮仍须实测；
3. **temp 草稿**带"未经人审"标注——参考价值打折，冲突以已审为准；
4. 用完必报 `kb_consulted`（热度遥测，供人工策展决策）。
