# P0：用户意图指导与旧材料清理

发布状态：本地草案；需求已确认，测试入口待确认。项目 issue tracker 与标签映射尚未配置，未发布 issue；发布时应用 `ready-for-agent` 对应标签。

## Problem Statement

用户能描述迁移目标，但不一定知道如何写出对 Porter 有帮助的意图文件。现有示例详略不一，缺少明确指南；P0 虽能读取意图，却没有明确约定如何将驱动类型、范围、约束和最终验收要求转化为本轮骨架决策。完整迁移验收与 P0 编译、载入验收容易混淆。

续跑时，用户修改显式传入的意图文件，工作区仍可能保留旧内容，造成用户目标与实际执行脱节。

仓库的新旧 P0 材料混杂，部分旧 skill 仍被其他阶段使用。简单批量删除可能破坏消费者；只整理文档，又不足以证明新 Porter 没有借用旧会话、知识或已完成的迁移成果。

## Solution

提供简短、可直接填写的 Markdown 模板、指南和示例，引导用户描述高层目标，尤其是驱动类型。允许自然语言、缺项和明确的未知信息，将源码调查与技术方案推导交给 Porter。

P0 使用意图决定骨架与接入方向，在现有工作区知识中说明采用的范围、约束及后续验收事项。显式传入的意图在续跑时生效，变化触发受影响决策和证据的复核。

按实际用途清理旧材料：删除失效内容，保留并重命名仍有消费者的 skill，修正当前阅读入口。同时从干净环境验证新 P0 的独立执行能力。

## User Stories

1. As a 迁移用户, I want a 简短的意图填写指南, so that 我能知道 Porter 需要什么信息。
2. As a 迁移用户, I want a 可直接填写的 Markdown 模板, so that 我无需从空白文档开始。
3. As a 迁移用户, I want a 展示合理信息深度的示例, so that 我能区分目标描述与实现方案。
4. As a 迁移用户, I want a 用自然语言描述驱动类型的方式, so that 我不必预先熟悉 Porter 内部类别标签。
5. As a 迁移用户, I want a 描述实际使用场景的位置, so that Porter 能理解迁移的用途。
6. As a 迁移用户, I want a 声明必须保留行为的方式, so that 必要语义不会在迁移中丢失。
7. As a 迁移用户, I want a 声明排除范围的方式, so that Porter 不会无意扩展任务。
8. As a 迁移用户, I want a 声明不可妥协约束的方式, so that 接入方案遵守我的限制。
9. As a 迁移用户, I want a 描述最终成功标准的方式, so that 后续迁移有清晰的验收方向。
10. As a 迁移用户, I want a 记录已知硬件和环境并允许填写“不知道”的方式, so that 未完成技术调查不会阻止我表达目标。
11. As a 迁移用户, I want a 接受自由组织内容的意图入口, so that 我不必为固定字段或标题调整已有文档。
12. As a 迁移用户, I want a 仅在关键歧义影响执行时发生的追问, so that 我不需要完成一轮强制问卷。
13. As a 迁移用户, I want a 由 Porter 调查文件范围、依赖和接线的流程, so that 高层需求不变成我必须提前完成的技术设计。
14. As a 迁移用户, I want a 能体现驱动类型和目标范围的 P0 骨架, so that 后续迁移从正确的接入方向开始。
15. As a 迁移用户, I want a 区分完整迁移验收与 P0 完成要求的执行过程, so that 最终功能要求不会自动扩大 P0 任务。
16. As a 迁移用户, I want a 明确声明 P0 特殊要求的方式, so that 本轮确有必要的额外约束能被识别。
17. As a 迁移用户, I want a 记录本轮范围、约束和后续验收项的知识文档, so that 我能检查 Porter 如何使用我的意图。
18. As a 迁移用户, I want a 不擅自缩减目标且如实记录源码事实的执行过程, so that 能力缺口不会被隐瞒或误当成功。
19. As a 续跑用户, I want a 显式传入新意图即可更新工作区目标的行为, so that 修改不会被旧副本忽略。
20. As a 续跑用户, I want a 未传意图文件时保留工作区目标的行为, so that 普通续跑无需重复提供输入。
21. As a 续跑用户, I want a 在意图变化后复核受影响决策和证据的流程, so that 历史成功不会掩盖新目标尚未满足的事实。
22. As a 续跑用户, I want a 在意图与人工回答冲突时明确追问的流程, so that Porter 不会静默选择互相矛盾的要求。
23. As a Porter 维护者, I want a 不包含失效 P0 指令的当前阅读入口, so that 新执行不会受旧协议误导。
24. As a 旧阶段使用者, I want a 清理后仍可找到所需 skill 的旧消费者, so that 文档整理不会意外破坏保留的功能。
25. As a 验证者, I want a 使用新工作区和干净目标源码的 P0 验证, so that 结果能说明新流程独立完成了本轮工作。
26. As a 验证者, I want a 明确记录允许资料、源码基线及本轮证据的结果, so that 我能分辨真实执行、历史成果和模拟测试。

## Implementation Decisions

- 修改用户文档入口、P0 意图输入与续跑处理、执行提示及知识写作约定，复用现有 CLI 和工作区知识机制。
- 指南涵盖驱动类型、使用场景、必须保留的行为、排除范围、硬约束、最终成功标准及已知硬件环境。驱动类型允许自然语言，由 Porter 核实并映射内部类别；不要求用户提前提供文件清单、依赖闭包或接线方案。
- 模板为写作辅助，不是必填 schema。继续允许不提供意图文件的既有用法；缺项不自动拒绝执行，也不引入固定标题解析器。仅对影响范围、硬约束或当前执行的歧义追问。
- 意图描述整个迁移目标。P0 用它决定骨架和接入方向，不自动将最终设备或完整功能验收转为本轮门槛；用户明确指定的 P0 特殊要求应单独识别。
- 保留当前 P0 基线：成功构建且有框架参与编译的证据、实际载入驱动且有本轮执行证据；单测失败或不可用按既有约定记录并延期。
- 在现有知识文档中记录本轮采用范围、骨架与驱动类型的关系、有效约束及后续验收项。不新增独立报告体系或机器语义判定系统。
- 源码事实必须如实记录，不能被用户意图覆盖；发现能力缺口也不能擅自缩减用户目标。意图与人工回答冲突时明确追问，不静默覆盖。
- 显式传入 `--intent-file` 时，以本次有效输入更新工作区意图；未传时沿用 `goals.md`。保留输入边界校验，无效输入不得破坏已有有效意图。
- 意图变化必须向续跑执行者明确呈现，并复核受影响决策和证据；无需因无关变化丢弃全部历史知识，也不得仅凭历史通过跳过复核。
- 清理按内容是否失效及实际消费者判断，不按文件名前缀判断。删除被替代的材料，历史通过 Git 保存；同步清除当前入口和引用中的失效指引。
- 仍被后续阶段使用的旧 skill 按实际用途重命名并更新消费者引用。旧流程文档移出当前阅读入口，清除失效 P0 指引。本轮不退役 P1–P7，不恢复新 P0 工作区尚未适配的下游执行。
- 干净验证使用新工作区、干净目标源码基线、指定意图和明确允许的参考资料，排除旧会话、工作区知识、旧执行日志及既有迁移成果。通过隔离验证环境完成，不清空用户已有工作区或修改用户现有目标树来伪造干净状态。

## Testing Decisions

- **待确认的主要测试入口：现有 P0 公共 CLI。** 优先通过 CLI 输入、工作区可观察内容、执行者收到的当前任务及返回结果验证行为，不新增生产测试接口。
- 复用现有自主 P0 集成测试先例：真实临时工作区、provider 替身、本地编译器与动态载入。现有意图输入测试已覆盖首次复制、输入错误、补充意图和旧续跑不覆盖行为；将旧行为断言调整为本次契约，避免为每个内部函数扩建测试。
- 覆盖首次意图输入；续跑显式更新；未传时保留；无效输入保留已有有效内容；更新后的意图传达给执行者并要求重新核实。用外部可见行为断言，避免固定整段 prompt 或 Markdown 标题。
- provider 替身可以验证输入传递与编排契约，不能证明真实 agent 理解了意图或正确解释了证据。真实运行需检查知识记录是否体现驱动类型、范围、约束和延期验收项。
- 对清理进行引用检查并运行受影响的旧消费者回归，证明删除、重命名没有留下失效加载路径；人工检查当前文档入口的一致性，不添加只锁定文件名或逐字文案的测试。
- 最终使用干净目标源码与新工作区进行真实 agent/目标 OS 的 P0 验证，记录基线、允许的资料、本轮编译参与证据、实际载入证据，以及意图如何影响骨架。完整功能要求应列为后续验收，不应无意阻塞默认 P0 完成。
- 本地动态载入测试不能替代真实目标 OS 验证；当前执行 agent 自验不能声称独立验证已经实现。如真实环境不可用，应明确记录未完成的验证，不能用旧日志补充为通过。

## Out of Scope

- 退役整个旧 Porter、删除全部 P1–P7 实现，或完成这些阶段与新 P0 的适配。
- 引入独立验证 agent、新的调度系统、知识协议或报告体系。
- 强制填写全部意图字段、要求固定格式、建立驱动类型分类体系，或默认逐项访谈。
- 让用户提前完成源码分析、文件划分、依赖解析或接线设计。
- 将完整设备功能、硬件交互或单测统一升级为默认 P0 完成门槛。
- 自动删除用户历史工作区、全局知识、日志或目标源码改动。
- 全仓代码清理或与本次意图使用及旧材料干扰无关的重构。

## Further Notes

- 已核实某些带旧 P0 名称的 skill 仍被手动骨架阶段和测试阶段消费；某些标题或文件名带历史名称的文档正文已是新设计。因此实施前必须核对消费者与正文，不可按名称批量删除。
