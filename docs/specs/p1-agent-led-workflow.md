# P1 主 agent 自主执行与部分完成交接

发布状态：本地规格草案；架构已确认，测试入口待确认。项目 issue tracker 和标签映射尚未配置，未发布 issue；配置后发布并应用 `ready-for-agent` 标签。

## Problem Statement

用户希望 P1 为驱动迁移提供精确的任务提示，并让 agent 根据源码和实际问题决定工作方法。现有流程固定执行策略分析、符号划分、依赖解环和裁剪处置，各角色的权限、顺序、输出和失败处理受到较强限制。后面的 agent 即使发现上游划分不合理，也难以重新组织方案。

用户仍要求模块尽可能小，但不要求每个拆分、依赖分析或解环子任务都在 P1 成功。当前流程遇错停止、要求无环依赖序，与允许记录待办并向后交接的需求不兼容。单纯缩短 skill 不能改变这些行为。

## Solution

由一个 P1 主 agent 对当前交付负责，自主选择步骤、顺序、重试、方案调整及子任务委派。保留“策略分析 → 符号划分 → 依赖解环 → 裁剪处置”为参考路线，不作为强制流水线。

主提示说明目标、用户约束、可用工具、交付要求和失败处理。主 agent 按当前问题生成精确的子任务提示；简单任务自行完成。现有四份 skill 中有价值的领域经验提炼为按需参考，不强制逐项执行。

P1 可以交付部分完成的结果。范围内源码必须归属模块或明确列为待划分，未解依赖如实保留。未完成工作进入 AUTO-TODO，故障及尝试进入 AUTO-FIXME。后续 agent 读取相关条目，自主决定先修复还是随实现解决，并更新完成证据。机器继续提供事实提取和检查，防止遗漏及虚假完成。

## User Stories

1. As a 迁移用户, I want P1 按我的功能目标开展分析, so that 技术上的困难不会静默缩减迁移范围。
2. As a 迁移用户, I want 模块尽可能小且功能内聚, so that 后续迁移可以细粒度增量推进。
3. As a 迁移用户, I want P1 遇到未解问题时保留有效成果, so that 局部失败不会迫使整轮工作作废。
4. As a 迁移用户, I want 区分完整交付和部分完成, so that 我知道哪些结果已经成立、哪些仍需处理。
5. As a P1 主 agent, I want 获得精简的任务目标和交付要求, so that 我能把注意力放在当前驱动的问题上。
6. As a P1 主 agent, I want 看到现有四步作为参考路线, so that 我有可用起点而无需遵守固定顺序。
7. As a P1 主 agent, I want 自主跳过、重复或调整参考步骤, so that 执行方式适应实际源码。
8. As a P1 主 agent, I want 自行完成简单任务, so that 不必为了遵循角色划分而创建子 agent。
9. As a P1 主 agent, I want 按实际问题委派独立子任务, so that 每个执行者获得精确且足够的上下文。
10. As a P1 主 agent, I want 修改模块边界、数量及技术迁移顺序, so that 新证据可以修正先前的设计。
11. As a 子 agent, I want 知道具体问题、必要上下文、约束和返回要求, so that 无需阅读整套流程规范也能完成任务。
12. As a 子 agent, I want 自主选择阅读和分析方法, so that 能针对问题找到合适的证据。
13. As a 子 agent, I want 挑战当前模块划分并提出修改, so that 明显不合理的上游决定可以被纠正。
14. As a 子 agent, I want 返回部分结果、失败原因及证据, so that 无需为了符合成功格式而编造结论。
15. As a P1 主 agent, I want 根据继续尝试的价值决定重试、换方法或延期, so that 不被每类子任务的固定重试次数绑住。
16. As a P1 主 agent, I want 使用现有事实提取、切片和检查工具, so that 不必手工重建机器已经能够提供的事实。
17. As a P1 主 agent, I want 按需读取领域经验, so that 能借鉴现有知识而不必执行所有启发式。
18. As a 后续迁移 agent, I want 接收已划分模块及明确的待划分源码, so that 不会把遗漏误认为用户排除的内容。
19. As a 后续迁移 agent, I want 看到真实依赖和未解环, so that 可以在当前工作中选择合适的处理办法。
20. As a 后续迁移 agent, I want 先推进不受未解问题影响的工作, so that 局部问题不会无条件阻断全部迁移。
21. As a 后续迁移 agent, I want 在受影响工作开始前获得相关待办, so that 能先修复或把修复纳入当前实现。
22. As a 后续迁移 agent, I want 获得问题影响、触发条件、已尝试方法和源码证据, so that 无需从头还原失败现场。
23. As a 后续迁移 agent, I want 自主选择具体修复阶段和方法, so that P1 不会提前规定尚缺上下文的实现方案。
24. As a 后续迁移 agent, I want 完成处理后更新待办和验证证据, so that 后续执行者能够判断问题是否仍然存在。
25. As a 迁移用户, I want 未解环或空执行序列不会被报告为全部完成, so that 进度反映真实工作状态。
26. As a 维护者, I want 复用现有 AUTO 文档及交接能力, so that 无需维护新的待办调度系统。
27. As a 验证者, I want 从实际入口和交接结果检查行为, so that 测试不依赖固定 prompt 文案或 agent 调用顺序。

## Implementation Decisions

- 修改 P1 编排 module、任务提示及其下游交接 interface，保留既有源码事实提取、切片、依赖检查和知识记录能力。新增行为应集中在现有 P1 交接 seam，避免建立平行流水线。
- 主 agent 对当前 P1 方案、任务分派和交付汇总负责。参考四步不再是强制角色、强制顺序或必须逐项成功的门槛；允许直接完成、按需委派、重复分析和回到上游修订。
- 主 agent 可以修改模块边界、数量和技术迁移顺序。子 agent 可以挑战并提出修改，由主 agent 统筹采纳。用户要求的保留行为、排除行为和硬约束不能被技术决定静默改变。
- “模块尽可能小”仍是优化目标，保留功能内聚及增量验证的考虑。不得因解环暂时失败而强制合并模块来制造成功；合并仍可作为主 agent 判断合适时采用的方案。
- 主提示只包含目标、约束、可用工具、交付要求和失败处理。子任务提示围绕具体问题生成，说明必要上下文、不可违反的约束、返回内容及未完成时的记录要求；不引入必须填写的新提示 schema。
- 四步的领域经验改为按需参考。保留有实际消费者需要的输出契约，不再把固定表格、分析顺序或启发式优先级作为 agent 的通用工作方法。
- 主 agent 决定子任务失败后重试、换方法或延期，只受整个任务的有效预算约束，不为各类子任务规定固定重试次数；本规格不指定新的预算数值。
- 子任务失败与 P1 交付状态分开表达。能够解释且有记录的未完成事项可以随部分结果交付，不因一个子任务失败自动丢弃其他有效结果；无法读取或可信交接的产物不能伪装为可用交付。
- P1 交付包括当前模块方案、源码归属、依赖事实及未完成事项。范围内源码必须明确归属或列为待划分，不能把未分配隐式解释为裁剪。依据用户范围进行的明确排除仍须保留理由。
- 已发现的依赖和环如实保留；依赖分析未完成时明确标注未知部分，不把未知解释为无依赖。合法拓扑序不再是所有部分交付的前置条件。
- 调整现有交接及下游执行状态的含义，使模块全集、已完成内容和待处理内容不只由可执行顺序推导。空顺序、残留环或待划分源码不能触发“全部模块已完成”。具体字段由实现按现有格式最小扩展，不预设新状态机。
- 后续先推进可推进的工作，在受影响任务开始前接手相关问题，可以先修复或纳入本任务实现；不能把未处理问题当成已满足的依赖。
- 复用 AUTO-TODO 记录未完成工作、影响、触发条件及完成条件，复用 AUTO-FIXME 记录故障、尝试、证据及后续修复和重验。主 agent 汇总子任务记录，不要求子 agent 竞争修改同一份知识文档。
- 后续任务提示要求读取相关 AUTO-TODO / AUTO-FIXME，自主安排处理并更新完成证据。P1 不为每条待办强制指定 P3 或 P4，也不引入将 Markdown 转为调度图的系统。
- 机器检查提供反馈并保护交付完整性，不替 agent 决定技术方案。必须防止源码遗漏、范围被静默更改和未完成被误报完成；不能用空实现、无条件成功或未经证明的不可达代替必要行为。

## Testing Decisions

- **待用户确认的主要测试 seam：现有 P1 公开执行入口到下游任务交接的业务路径。** 使用真实临时工作区和现有编排、记录、检查与交接实现；仅替换 agent provider 及不适合测试环境执行的外部构建效果，不新增生产测试接口。
- 测试可观察行为：接收的任务目标、产物、源码去向、依赖事实、待办、交接结果和完成状态。不断言 agent 必须调用某个角色、执行固定步骤、重试固定次数或输出逐字相同的提示。
- 复用现有 P1 导入测试中的小型合成驱动与双模块循环依赖案例；复用业务交接测试保留真实编排、仅替换 provider 的方式，以及 AUTO 文档和迁移状态测试的现有能力。
- 覆盖简单任务由主 agent 直接交付，以及主 agent 收到子任务失败后调整方案或延期。确认编排器允许这些不同路径，不要求某一种策略每次出现。
- 覆盖有环和无环模块并存、部分源码待划分、依赖分析未完成及裁剪处置延期：有效成果可交接，问题及证据被保存，不受影响工作可推进，受影响任务收到处理义务。
- 覆盖空依赖顺序、有环、未归属源码及未完成事项不会被报告为全量完成；明确裁剪与待划分保持可区分。
- 覆盖下游读取相关待办、处理后写回完成证据；续跑仍能区分已处理和未处理内容，不因前一轮局部失败遗失有效交付。
- 保留有效完整交付的回归，验证模块参考源码、归属和功能约束仍可被现有消费者读取。需要调整与新部分完成语义冲突的旧断言，不机械删除输入有效性检查。
- provider 替身验证执行与交接契约，不能证明真实 agent 的拆分质量。真实 agent 验证应检查是否能根据具体问题调整步骤、保持小模块目标并给出可信延期记录；不能仅凭流程返回成功声称迁移语义正确。

## Out of Scope

- 将“模块尽可能小”替换为减少依赖或减少解环次数的优化目标。
- 要求 P1 解决所有依赖环、完成所有裁剪处置，或对每个子任务强制成功。
- 新建通用工作流引擎、待办调度系统、固定角色体系或大型 skill 框架。
- 强制 agent 每次委派、固定并行度、固定分析方法或固定重试次数。
- 放宽用户功能范围、删除必要的输入检查，或允许虚假完成。
- 全面重写后续迁移阶段；本次只调整接受部分交付、接手待办及正确反映完成状态所需的行为。
- 改变源码物理切片机制、引入新的迁移表示或取消现有源码参考产物。
- 在本次规格整理中实现功能、修改运行中的迁移工作区或声称已通过功能测试。

## Further Notes

架构选择来自已确认的讨论：主 agent 有权重划；保留尽可能小的模块目标；子任务可失败并延期；主 agent 决定重试；源码必须归属或显式待划分；下游自主接手相关待办；四步仅为参考。

现有流程仍有遇错即停、依赖无环顺序和裁剪就绪门槛，因此本需求不能仅靠改写 skill 完成。允许部分交付必须同时修改实际交接和下游完成判断。
