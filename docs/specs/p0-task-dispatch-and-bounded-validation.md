# P0 任务派发、任务 skill 与有界验证

发布状态：本地规格；需求与测试入口均已确认。项目 issue tracker 与标签映射尚未配置，未发布 issue，未应用 `ready-for-agent` 标签。

## Problem Statement

Porter 的统一准备流程允许主 agent 直接调查、修改代码和执行验证。大任务的执行边界依赖主 agent 自行把握，可能长时间停留在一次主 agent 调用内，没有通过宿主提交可供接续的任务交接记录（handoff）。原生子 agent 的调用也不等同于宿主管理的派发、结果记录和知识沉淀。

通用任务描述不足以说明不同工作的调查维度、交付要求和停止条件。执行者容易扩大调查或验证范围，用户难以判断当前工作是否服务于本阶段验收。

补充验证缺少按目标记录的一次尝试边界。骨架已有实际构建和载入证据时，非必要单测仍可能因更换参数或延长超时而反复执行。迁移规划和补充验证处于同一任务时，补充验证失败也可能拖延规划交付。

用户需要明确的大任务派发、可审查的任务目标以及有界的失败处理，同时保留主 agent 按证据安排工作的能力。

## Solution

主 agent 负责理解意图、拆分任务、判断必要性、核对证据和执行验收，可以进行服务于这些职责的少量核对。源码专项调查、骨架实现与构建载入验证、迁移规划及补充验证通过宿主管理的子任务执行。

提供三类任务 skill，由主 agent 按需选用，不要求每次运行依次执行所有类别：

1. 源码与依赖调查。
2. 原生骨架实现、构建与载入验证。
3. 迁移规划、补充验证。

派发前明确每个目标的范围、完成条件、证据要求、必要性和停止条件。必要性依据本阶段验收与用户明确要求判定。规划结论与补充验证结果分别交付；补充验证失败或超时后延期到 AUTO-TODO，不阻塞已完成规划的验收。

补充验证按目标只尝试一次。更换任务名称、命令、参数或超时不产生新的尝试资格。必要任务仅在存在失败证据及针对性修正时重试，否则提交阻塞交接；所有执行仍受整轮时间预算约束。

## User Stories

1. 作为迁移发起者，我希望主 agent 从意图中识别本阶段验收要求，以便完整迁移目标不会自动变成本轮必须完成的业务实现。
2. 作为迁移发起者，我希望大任务通过宿主派发给子 agent，以便执行进度、交付和失败均有可审查记录。
3. 作为迁移发起者，我希望主 agent 保留少量核对能力，以便简单的证据确认无需额外派发完整任务。
4. 作为主 agent，我希望按需选用三类任务 skill，以便任务安排符合实际依赖和已有证据。
5. 作为主 agent，我希望已有调查和交付可以复用，以便无需为了覆盖全部 skill 而重复执行任务。
6. 作为源码调查执行者，我希望知道需要核对的源端行为、入口、依赖和目标能力，以便调查结果能支持骨架实现和迁移规划。
7. 作为源码调查执行者，我希望分别记录能力已具备、缺失和未知，以便未知项不会被当作已实现的依赖。
8. 作为骨架执行者，我希望实现、接线、构建和载入属于同一任务范围，以便能围绕实际证据完成必要修正。
9. 作为骨架验收者，我希望看到框架参与编译的记录以及本轮实际载入证据，以便源码中的打印语句或无关构建不会被当作通过证明。
10. 作为迁移规划执行者，我希望明确迁移范围、模块职责、源码归属和依赖顺序的交付要求，以便交付可供审阅的建议性迁移规划。
11. 作为迁移规划执行者，我希望补充验证有独立结果，以便验证失败时仍能交付已完成的规划。
12. 作为主 agent，我希望在派发前说明目标是否验收必需及其依据，以便执行者清楚哪些失败必须阻塞。
13. 作为迁移发起者，我希望我明确提出的阶段要求优先，以便必要测试不会被错误标记为补充验证。
14. 作为补充验证执行者，我希望使用最窄的有效范围并预先设置超时，以便一次尝试有明确边界。
15. 作为补充验证执行者，我希望失败或超时后立即记录已知结果和停止原因，以便无需继续排障才能完成交付。
16. 作为迁移发起者，我希望同一补充验证不会通过改名、换参数或延长超时继续执行，以便一次尝试限制真实有效。
17. 作为主 agent，我希望宿主拒绝已尝试补充验证的重复派发，以便执行约束不只依赖自然语言提醒。
18. 作为续跑使用者，我希望补充验证的尝试记录被保留，以便重启会话或续跑不会清空一次尝试限制。
19. 作为任务执行者，我希望任务启动后即记录尝试状态，以便中断后的恢复不会把已启动验证当作从未执行。
20. 作为主 agent，我希望保留必要任务的失败证据并注明针对性修正，以便重试有可审查依据。
21. 作为迁移发起者，我希望缺少新依据的必要任务提交阻塞交接，以便不会无限进行相同尝试。
22. 作为知识 agent，我希望收到补充验证失败的证据、已知原因或未知原因、处理条件和完成条件，以便形成可执行的 AUTO-TODO。
23. 作为后续迁移执行者，我希望 AUTO-TODO 能定位原始交接和日志，以便不必重新发现未完成工作的上下文。
24. 作为知识 agent，我希望继续独占共享知识写入权，以便不同执行者不会各自修改相互矛盾的知识记录。
25. 作为主 agent，我希望在最后一批任务结果沉淀后确认知识收据，以便任务延期不会被遗漏在整体完成状态之外。
26. 作为迁移发起者，我希望骨架与规划分别验收，以便补充验证失败不会掩盖已经完成的工作。
27. 作为迁移发起者，我希望设备缺失、模拟数据和真实设备验证有明确区分，以便 P0 成功不会被误读为完整设备功能已经通过验证。
28. 作为维护者，我希望从公开 CLI 验证派发、停止、续跑和知识沉淀行为，以便测试不绑定内部函数组织。
29. 作为维护者，我希望任务 skill 和规格只陈述适用事实、要求及边界，以便阅读者无需了解设计讨论或历史演变。
30. 作为迁移发起者，我希望整个过程维持单一代码写入者和整轮预算，以便任务拆分不会引入并发修改冲突或无限运行。

## Implementation Decisions

- 延续统一准备流程、骨架与规划分别验收、主 agent 独占验收权、专门知识 agent 持续维护共享知识的职责划分。迁移规划是建议性 plan，不能替代用户对迁移范围的决定。
- 主 agent 按需选用三类任务 skill；不设置必须完成的类别清单，不引入固定阶段流水线。已有有效证据足以支持结论时允许直接核对和验收。
- 大任务通过宿主派发执行。主 agent 不使用原生子任务工具或另起 agent 进程绕过宿主；子任务不继续委派。宿主保持顺序执行和单一代码写入者约束。
- 三类 skill 共享任务身份、目标、范围、输入指针、完成条件、证据、必要性和停止条件的约定，分别补充本类工作的调查与交付内容。只加载本任务需要的 skill 和相关材料，不全量注入知识。
- 源码与依赖调查覆盖源端职责、注册与匹配入口、关键行为与状态、目录内源码归属、目录外依赖，以及目标 OS 的对应接口和先例。依赖区分已具备、缺失和未知，列出最小必要能力关系及证据；已足以支持派发和规划时交付，未知项如实保留。
- 骨架实现与构建载入验证覆盖原生接口、注册和初始化接线、最小实现、实际构建及实际载入。明确工作目录、前置条件、命令、日志位置和结果。入口明确时执行，只补查影响当前失败的信息；针对必要失败修正后复验。
- 骨架验收要求编译记录、依赖或产物证明框架实际参与构建，并有本轮目标 OS 支持方式的载入证据。不能以手写输出、源码打印语句、无关构建、mock 或设备协议自测替代实际载入。
- 迁移规划与补充验证覆盖纳入和排除的迁移范围、迁移模块职责与源码归属、真实依赖、建议迁移顺序及未知项。补充验证仅在有具体问题时按需开展，说明最窄验证范围、有效机制、日志位置和成功失败特征；没有可用验证机制时记录事实。
- 合并任务内区分规划交付与补充验证目标。任务整体可以交付规划并报告验证延期，不以单一成功或失败值覆盖两者。一个已完成规划不因补充验证失败而要求重新执行。
- 主 agent 派发前将每个执行目标标记为验收必需或补充验证，并给出依据。用户明确的本阶段要求优先。完整设备业务行为和完整单测默认不构成 P0 门槛，补充验证失败本身不能成为提高必要性的理由。
- 宿主在现有工作区状态中持久保存最小任务与尝试记录：稳定任务身份、验证目标、任务类别、必要性与依据、尝试状态、结果和交接引用。合并任务中的补充验证有可单独识别和持久记录的目标。
- 对补充验证，一次是围绕同一验证目标的一次实际尝试。允许为首次尝试完成必要准备；实际验证失败或超时后停止该目标，不在同一任务内部修正后重跑，也不在返回后继续派发。改变命令、参数、超时或名称仍是同一目标的重试。
- 宿主在启动目标前持久记录尝试，拒绝已尝试补充验证的重复派发，并将拒绝原因返回主 agent。续跑及会话重建保留该限制。主 agent 负责识别改名但目标相同的请求；宿主不实现自然语言语义判重系统，也不能宣称已完全检测 agent 内部的所有命令重试。
- 补充验证的普通失败、超时或对应执行调用失败保留日志和已有交接，转为延期记录；在整轮预算仍足够且共享状态有效时继续流程。不把全局预算耗尽、用户中断或共享知识保护失败解释成可以忽略的补充验证失败。
- 必要任务允许有依据的修正与重试。重试记录必须引用失败证据并说明针对性修正；主 agent 判断其相关性，宿主检查必需记录是否具备。无新依据时提交阻塞交接，不以改名或延长超时代替修正。沿用整轮时间预算，不新增任意次数上限。
- AUTO-TODO 由知识 agent 根据交接维护。延期条目包含验证目标、来源和证据、已知失败原因或原因尚未知、未完成内容、影响、后续处理触发条件与完成条件；无需先查明根因才允许延期。其他执行者不能直接写共享知识。
- 补充验证延期不直接否定已完成规划，但主 agent 仍需检查失败是否揭示验收依据存在问题。有事实影响的验收需复核；不能为了清空待办而削减用户要求或把未验证内容写成通过。
- 整体完成仍要求骨架和规划分别通过、所有应沉淀结果已交给知识 agent，且主 agent 已确认最后一批知识。补充验证可以留有 AUTO-TODO；知识维护失败不能冒充整体完成。
- 文档只陈述当前适用的事实、要求、证据与约束，不描述历史实现、恢复过程或方案演变。事实、推断和未验证内容明确区分。

## Testing Decisions

测试入口已确认：复用公开 CLI 与本地 opencode 可执行替身这一现有集成入口，覆盖工作区输入、统一执行循环、provider 调用及持久结果。不新增专用内部测试接口。

- 好的测试从用户可见行为判断结果：provider 实际调用、退出状态、任务交接、持久尝试记录、验收和 AUTO-TODO。避免仅检查提示词包含某句话、内部函数被调用或 JSON 自称成功。
- 复用现有 CLI 集成测试的子任务派发、选定材料传递、知识会话续接、两项验收、证据失效复核、任务中断和本地编译载入案例。
- 验证主 agent 可以按需选择任一任务类别，不必依次执行三类；子任务得到所选 skill 和必要材料，交付经主 agent 与知识 agent 接续处理。
- 验证补充验证首次失败、超时或执行调用失败后记录延期；剩余必要工作能够继续，规划可独立验收，知识 agent 生成有证据和处理条件的 AUTO-TODO。
- 验证合并任务中的规划完成与补充验证失败分别保留，宿主不会因验证失败重跑整个规划任务。
- 验证同一目标更换显示名称、命令参数或超时仍无第二次派发资格；测试使用稳定目标身份，不把该案例描述为自然语言语义判重能力。
- 验证目标启动后中断再续跑保留尝试记录，不意外授予补充验证第二次执行资格。
- 验证必要任务具有失败证据和针对性修正记录时可以重试；缺少记录时拒绝再次执行并保留阻塞原因。证据是否足以支持修正的语义判断仍由主 agent 负责。
- 验证补充验证失败不会自动改变必要性，用户明确的阶段要求仍作为验收依据传递给主 agent。
- 验证拒绝重复派发会返回可处理的原因，而非抹去已有成功规划、验收证据或交接。
- 验证最后一批延期事项尚未沉淀、知识维护失败或主 agent 尚未确认知识时，整体不能标为完成。
- 保留输入与证据改变后复核、单一写入者、整轮预算和执行中断的现有保护。
- 确定性替身只能验证宿主契约，不能证明真实模型始终遵守职责边界或一次尝试规则。真实 P0 验证另行检查实际子任务派发、原始调用日志、任务停止条件和知识结果，不以固定字符串测试代替这类检查。
- 真实 P0 的模型实验不作为本地测试的网络依赖；编译载入替身案例也不作为真实目标 OS 或 Flash 设备验证的证明。

## Out of Scope

- 完整 SPI-NOR 或其他驱动的业务迁移、真实设备读写擦除验收，以及默认要求本阶段全部单测通过。
- 固定执行所有任务类别、并行代码写入、多级子任务委派和通用 DAG 调度系统。
- 宿主对任意自然语言目标的语义等价判断、对任意 shell 命令的完整语义解析，以及把模型行为约束宣称为已完全机器强制。
- 为必要任务增加独立的任意重试次数上限，或为补充验证失败自动扩大本阶段验收范围。
- 引入新测试框架、公开新的内部测试接口或要求本地集成测试访问真实模型。
- 自动处理进程宿主消失的通用生命周期重构、运行监控界面和跨驱动知识同步。
- 本规格编写过程中实施功能、自动启动新的迁移实验或修改模型默认值。

## Further Notes

- 本规格遵守统一准备、分别验收、单一代码写入者与专门知识 agent 的架构约束。任务类别并不构成必须逐项执行的阶段。
- 延期表示有明确后续条件的未完成工作，不表示验证通过，也不要求本轮解决所有未知项。
- 项目 issue tracker 和标签映射尚未配置。需运行 `/setup-matt-pocock-skills` 完成项目配置，再发布本规格并应用 `ready-for-agent`，无需额外 triage。
- 本规格对应功能已实现。公开 CLI 集成测试和类型检查通过，审查与验证结果见
  [审查记录](../reviews/p0-task-dispatch-and-bounded-validation.md)。真实 P0 模型实验尚未重新运行，issue 尚未发布。
