# P0 骨架与三个验证循环

2026-09-08 访谈确认并实现的编排契约。

执行顺序：输入解析、类别识别 → 零功能骨架发现与落盘 → 编译 loop →
启动/设备注入 loop → 单测 loop → P0 门禁 → P1。

骨架包含构建接线、注册/设备认领日志、探针落点和最小单测。不实现
寄存器操作、DMA 或收发等驱动业务功能。

## 编译 loop

同一 loop 按顺序验收四项，失败时依据证据修正后重验：

1. 定义完整、可复现的编译方式，包括环境、命令、参数和产物。
2. 证明生成的骨架代码在编译范围内。
3. 仅编译对应模块及其依赖，生成目标 OS 原生模块产物，不生成完整镜像。
   不强制 `.so` 后缀，实际格式由目标构建系统决定。
4. 局部构建通过后生成完整镜像。

## 启动/设备注入 loop

启动与设备注入属于同一个 loop。验收同时要求：

- 注入设备后，骨架确实识别/认领设备。
- 目标 OS 进入 shell；编排器发送命令，收到本轮唯一标记，证明命令往返。

不要求零功能骨架完成设备业务交互。

## 单测 loop

使用目标 OS 原生测试机制，仅运行骨架所属模块的最小测试。允许启动
专用测试内核，无须进入完整系统的交互 shell。

Asterinas 的内核态测试使用 `cargo osdk test` 启动 QEMU；无内核依赖的
crate 可使用 `cargo test`。ELF 是文件格式，不能据此判定运行在用户态。
参见 [Asterinas 测试说明](https://asterinas.github.io/book/kernel/advanced-instructions.html)。

## P2 调整

P2b 的发现与施工提前至 P0，原独立三信号验证由上述三个 loop 承担。
取消重复验证，验证失败可以修正骨架。

默认流程暂时跳过 P2a 主轴提取与批量映射，保留手动 `p2-map` 入口和
已有映射数据。骨架验证所得接口记录、P3 按模块增量映射继续保留。

## 实现与兼容

P0 先调用骨架施工，再执行三个验证 loop；施工 manifest 标记 `applied`，
三个 loop 全部通过后才标记 `verified` 并记录接口证据。T5 只检查证据，
不重复跑测试。原四 session 的 runner 不会直接作为新门禁的通过依据。

骨架产物路径暂保留在 `P2/reports/scaffold_*`，供现有探针和迁移消费者
读取。手动 `p2-scaffold` 保留旧式独立校准入口；默认 P2 不再调用它。
P0 可用 `--device-ids` 指定认领键，也可从 Linux 源码及迁移意图发现。

runner 的新增字段及 agent 执行契约见 [环境提取指令](../skills/P0-env-extract.md)。
源码或已收敛片段改变会使前序验收失效并重跑；幂等复用要求源码与
runner 的指纹一致。局部产物、镜像和编译范围证据均由命令实际验收。

## 验证记录

`python3 -m unittest discover -s tests`：369 通过，3 跳过（共 372 项）。
新增回归实际执行本地编译器、交互 shell 和测试程序，覆盖局部构建失败、
镜像越界生成、过期产物、伪交互、无设备、无关测试、源码修正重验、旧
runner 续跑，以及没有 P2a/P2b 交接记录时的默认 P2 流程。

本地 Asterinas 也通过新交互执行器验证：发送随机标记、收到 guest 独立
响应、正常关机且退出码为 0。复现脚本与日志分别为
`migrations/local-build/check-p0-executor.py`、
`migrations/local-build/p0-interaction-executor.log`。

完整 agent 自动发现的 P0 尚未实跑：当前宿主 PATH 中没有 `opencode`。
上述 Asterinas 实测使用已有基线镜像，不能替代新迁移骨架的端到端验收。
