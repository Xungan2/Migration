# P0 骨架与三个验证循环

2026-09-08 访谈确认并实现的编排契约。

执行顺序：输入解析、类别识别 → 最小前置依赖识别与就绪检查 → 零功能骨架发现与落盘 → 编译 loop →
启动/设备注入 loop → 单测 loop → P0 门禁 → P1。

## 最小前置依赖

`p0.prerequisites.discover` 从源驱动的注册、匹配和接口调用识别最小依赖图，
允许沿 Linux 参考根读取输入目录外的提供者。目标硬件/仿真平台未定时，
先生成选择任务；依赖不按 SPI、PCI 或软件设备等类别硬编码。

每项记录必要性、提供者源码文件、依赖关系、目标侧接口及接线证据、最小
补齐范围和完成条件。状态为 `available`、`missing` 或 `unknown`；可用项
必须提供目标源码原文证据，且它的依赖也须可用。引用、路径及无环性由脚本
校验，能力对应关系由 agent 调查；源码证据不能替代后续运行验收。

产物位于 `P0/reports/`：

- `prerequisites.json`：完整依赖分析。
- `prerequisite_tasks.json`：按依赖顺序生成的缺失/待确认任务及阻塞关系。
- `prerequisite_tasks.md`：可交给前置迁移任务执行者的源码范围、目标树和完成条件。

存在 missing/unknown 时，`p0.prerequisites` 发布失败 handoff、登记同名
关口并返回 3，主驱动骨架和三个 loop 均不执行，旧骨架也不能跳过检查。
此步骤不自动执行前置迁移，不扩展主驱动的 P1 文件白名单。

前置任务完成后重跑原 P0 命令即可；每次调用都以独立发现 execution 重新
核对当前源码，避免只检查旧引用而漏掉新增的总线/控制器代码。人工完成
标记和关口答案不是放行依据。所有依赖可用后关闭关口；报告未变时保留
原就绪 handoff，允许下游复用。T5 再检查依赖报告及就绪证据。

对已有旧骨架，依赖检查仍会先执行；没有绑定该就绪步骤的旧发现不能作为
新流程的前置证据，应在新工作区生成骨架，保留原目标树改动供核对。

例如，输入驱动依赖目标尚未提供的总线或控制器时，生成相应的最小补齐
任务，而不是改为认领其他设备、打印 MISS 或通过命令行改变日志来放行。

## 骨架发现

骨架发现拆为 `p0.scaffold.build`（构建接线）、`p0.scaffold.device`
（认领与注入）、`p0.scaffold.test`（最小测试与探针），最后由
`p0.scaffold.recipe` 生成施工单。四个子任务各用独立 session，按顺序
通过 handoff 交接；同一子任务内的输出修订复用自己的 session。
发现文件存于 `P0/reports/scaffold/`，字段及源码证据验收后发布 handoff。
这些是发现/方案成果，不表示编译或行为已经通过。

静态施工发布 `p0.scaffold.apply`，后续依次交接给 `p0.loop.build`、
`p0.loop.boot`、`p0.loop.unit_test`。每个 loop 有独立 session，真实
命令和日志验收通过后才发布成功 handoff。provider 超时或失败结束本次
execution；重跑以新 session 读取失败 handoff，已完成且仍有效的前置
子任务复用，不重新调查整棵树。手动 P2 校准入口保留原流程。

发现中超出 P0 的有用信息由施工 agent 整理为 `deferred_findings`，保留
主题、适用任务/阅读条件、内容、证据与确认状态。porter 将其另存为
`P0/reports/scaffold/followup.json` 并发布 `p0.scaffold.followup` handoff。
P1、P2 映射和 P3–P5 读取该 handoff 的主题索引，遇到对应需求时读取详细
资料并核对当前源码；它不代表功能已实现，也不参与 P0 通过判定。

骨架包含构建接线、注册/设备认领日志、探针落点和最小单测。不实现
寄存器操作、DMA 或收发等驱动业务功能。

## 编译 loop

同一 loop 按顺序验收四项，失败时依据证据修正后重验：

1. 定义完整、可复现的编译方式，包括环境、命令、参数和产物。
2. 证明生成的骨架代码在编译范围内。
3. 仅编译对应模块及其依赖，生成目标 OS 原生模块产物，不生成完整镜像。
   不强制 `.so` 后缀，实际格式由目标构建系统决定。
4. 局部构建通过后生成完整镜像。

## 启动/设备注入 loop

启动与设备注入属于同一个 loop。验收同时要求：

- 注入设备后，骨架确实识别/认领设备。
- 目标 OS 进入 shell；编排器发送命令，收到本轮唯一标记，证明命令往返。

不要求零功能骨架完成设备业务交互。

## 单测 loop

使用目标 OS 原生测试机制，仅运行骨架所属模块的最小测试。允许启动
专用测试内核，无须进入完整系统的交互 shell。

Asterinas 的内核态测试使用 `cargo osdk test` 启动 QEMU；无内核依赖的
crate 可使用 `cargo test`。ELF 是文件格式，不能据此判定运行在用户态。
参见 [Asterinas 测试说明](https://asterinas.github.io/book/kernel/advanced-instructions.html)。

## P2 调整

P2b 的发现与施工提前至 P0，原独立三信号验证由上述三个 loop 承担。
取消重复验证，验证失败可以修正骨架。

默认流程暂时跳过 P2a 主轴提取与批量映射，保留手动 `p2-map` 入口和
已有映射数据。骨架验证所得接口记录、P3 按模块增量映射继续保留。

## 实现与兼容

P0 先调用骨架施工，再执行三个验证 loop；施工 manifest 标记 `applied`，
三个 loop 全部通过后才标记 `verified` 并记录接口证据。T5 只检查证据，
不重复跑测试。原四 session 的 runner 不会直接作为新门禁的通过依据。

骨架产物路径暂保留在 `P2/reports/scaffold_*`，供现有探针和迁移消费者
读取。手动 `p2-scaffold` 保留旧式独立校准入口；默认 P2 不再调用它。
P0 可用 `--device-ids` 指定认领键，也可从 Linux 源码及迁移意图发现。

runner 的新增字段及 agent 执行契约见 [环境提取指令](../skills/P0-env-extract.md)。
源码变化后，内容未变的已收敛配置先对新源码执行真实重验，失败再交给
新 session 修正；配置片段改变则重新发现，不能沿用旧通过状态。
源码或已收敛片段改变会使前序验收失效并重跑；幂等复用要求源码与
runner 的指纹一致。局部产物、镜像和编译范围证据均由命令实际验收。
