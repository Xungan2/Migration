# 写一份对 Porter 有帮助的迁移意图

描述你想用迁移后的驱动做什么，以及必须守住的边界。几段自然语言即可，
不需要先分析代码、列文件清单或设计接线方案。意图描述整个迁移目标；
统一准备流程用它选择骨架与接入方向、确定迁移范围和建议规划；骨架须实际编译与载入。

直接使用自己的 Markdown 文档即可。
不必保留标题或填满每项；未知信息写“不知道”，没有特殊限制就省略。

| 想清楚什么 | 可以怎样写 |
| --- | --- |
| 驱动类型 | “软件块设备框架”“SPI-NOR Flash 存储驱动”“PCIe 网卡”；不必知道内部类别标签 |
| 使用场景 | 谁通过什么方式使用它？例如“在目标 OS 创建读回全零的虚拟块设备” |
| 必须保留的行为 | 对用户可见的正常行为、关键错误处理和资源释放要求 |
| 排除范围 | 本轮不需要的设备、协议、兼容接口或功能 |
| 硬约束 | 必须使用的语言、原生接口、安全约束，以及不能接受的简化 |
| 最终成功标准 | 能观察到哪些行为才算完整迁移成功；避免只写“测试通过” |
| 已知环境 | 目标 OS、设备型号、板卡或模拟环境、可用工具；不确定就写明 |

Porter 负责核实类型、映射内部类别、调查源码范围与依赖。`--category` 可选，
可作为类别提示；它与意图冲突且影响当前工作时，Porter 会追问。
只有影响范围、硬约束或当前执行的歧义需要回答，不会默认逐项访谈。

例如，[dm-zero 示例](../examples/dm-zero-intent.md)说明软件块设备的功能边界。
最终业务验收不自动变成骨架验收门槛。确有特殊要求时单独写“本轮 P0 要求”。

```bash
python3 porter/main.py prepare \
  --linux-driver linux-5.10/drivers/md --target-os asterinas \
  --output-dir migrations/my-port --intent-file examples/dm-zero-intent.md
```

首次输入保存为工作区 `goals.md`。续跑显式传 `--intent-file` 会用有效文件更新
该副本；不传则保留工作区版本，也可以直接编辑 `goals.md`。文件需为非空 UTF-8。
更新会触发受影响决策和证据的复核；错误输入不会覆盖已有有效意图。
如果你直接编辑了工作区副本，续跑时应省略 `--intent-file`，避免用外部旧版本覆盖它。

在工作区 `knowledgebase/` 查看采用的范围、类型与骨架关系、约束和延期验收项。
能力缺口应被记录，不能被悄悄解释成缩小目标。需要澄清的问题写在本轮报告中；
将回答写入 `answers.md` 后重跑。人工回答与意图冲突时，Porter 会明确追问。
